# Establish an independent OMNIA Deployment Domain

The Deployment Domain defines versioned request and execution contracts; it is not a central deployment service. The contracts and validators in this repository implement structural validation, immutable artifact identifiers, approval metadata, and execution outcomes only. They do not execute deployments, prove identity or approval, or configure infrastructure.

Each application repository owns its CI/CD workflow, independent deployment identity, and least-privilege credentials; GitHub Actions is the execution engine. A workflow must bind its run to the service repository, verify the requested artifact digest and source provenance, and enforce production authorization using a trusted identity and approval system. `initiatedBy`, `approvedBy`, `approvedAt`, `approvalReference`, and `approvedScopeDigest` are claims and audit locators, not authorization evidence by themselves. Before acting, a workflow must authenticate the initiating actor, retrieve and validate the referenced approval record, and compare its approved scope digest to the request. The scope digest is SHA-256 over RFC 8785 JSON Canonicalization Scheme bytes for the full request object with `authorization` replaced by only its `requestId`, `initiatedBy`, and `approvalRequired` fields; this binds approval to the deployment, service, environment, target, artifact, adapter, operation, migration and rollback metadata, and any request extensions. Schema validation cannot establish that the referenced record is trusted, that the digest was approved by an authorized person, or that credentials are least-privilege.

Production authorization, protected-environment policy, credentials, and deployment permissions must be enforced by GitHub Actions and its trusted approval provider, not by browser clients, SERVITOR, or schema validity. Read-only operations access is separate from deployment permission. SERVITOR may eventually request an approved workflow through a constrained interface but does not execute deployments, hold deployment credentials, or receive unrestricted production shell access. STRATEGIUM is the operator interface; MAGOS remains the operational source of truth. MAGOS and STRATEGIUM status reporting is a future integration, not implemented by these contracts. NOOSPHERE independently monitors host and service health.

Deployment workflows are responsible for preflight checks, deployed artifact digest and version verification, service health verification, and reporting execution outcomes. Application rollback is a distinct operation and is not database rollback. A successful rollback execution must report the prior artifact digest as deployed and a successful rollback outcome. Database migrations must state compatibility, require explicit approval, and declare required backup/restore preflight; backups, restores, pruning, and other destructive or operational actions are separate actions requiring explicit authorization, not ordinary deployments.

The initial targets are MAGOS and Ice IQ (currently Docker Compose), ARCHIVIST and NOOSPHERE (currently Node.js/systemd), and Operations MCP and STRATEGIUM (deployment model to be established). These are target examples, not adapter bindings or assumptions about eventual deployment mechanisms; SERVITOR may be added later. Existing MAGOS-owned `Deployment` snapshots and `deployment.started`, `deployment.completed`, and `deployment.failed` event contracts remain unchanged. New request and execution schemas supplement rather than replace them. The v1 schemas are pre-adoption drafts; consumers must update together before adoption of the tightened approval-evidence and execution-digest requirements. Subsequent incompatible changes require a new major schema identifier with old and new majors coexisting during migration.
